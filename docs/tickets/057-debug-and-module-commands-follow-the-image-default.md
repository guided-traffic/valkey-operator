# T57 - enable-debug-command and enable-module-command follow the image default

The scope is all three protected-action switches: `enable-debug-command`, `enable-module-command`
and `enable-protected-configs`. The operator-facing statement is gap
[H-7](../security/secrets-and-tls.md#h-7).

## Current state

- `generateValkeyConf` ([`configmap.go:62-138`](../../internal/builder/configmap.go)) renders none
  of the three switches; its `# General` block
  ([`configmap.go:116-124`](../../internal/builder/configmap.go)) is where they would go. The data
  container runs `valkey-server <config>` directly
  ([`statefulset.go:822-833`](../../internal/builder/statefulset.go)), so the compiled default of
  the `valkey-server` in `spec.image` decides. `spec.image` is required and chosen by the CR author
  ([`valkey_types.go:1032-1034`](../../api/v1/valkey_types.go)); the pins in
  [`images.go`](../../test/testimages/images.go) decide only what CI runs.
- The operator issues no `CONFIG SET`, `DEBUG` or `MODULE`, and the CRD has no free-form config
  field, so a CR author cannot set these directives and the `no` default costs the operator nothing.
- **The default is `no` and immutable everywhere upstream.** `src/config.c` of `valkey-io/valkey`
  defines all three as `IMMUTABLE_CONFIG` with default `PROTECTED_ACTION_ALLOWED_NO` on every tag
  from `7.2.4-rc1` through `9.2.0-rc1` and on `unstable`.
- **Both pins refuse all three actions** (docker, `valkey/valkey:9.1.1` and `valkey/valkey:8.1.9`,
  uid 999): `CONFIG GET` returns `no` for each switch; `CONFIG SET` of each is refused as immutable;
  `DEBUG SLEEP 0` and `MODULE LOAD` are refused, also from inside the container; `CONFIG SET dir`
  and `dbfilename` are refused as protected, while an unprotected config such as `maxmemory-policy`
  answers `OK`. A config generated by `generateValkeyConf` plus the three lines set to `no` boots
  and behaves identically.
- **A multi-key `CONFIG GET` returns the keys in an unspecified order** (8.1.9 gave three orders
  in three runs), so a test must read one key per call.
- **Sentinel is out of scope.** `valkey-sentinel` accepts the three lines, and `DEBUG` and
  `MODULE` are unknown commands in sentinel mode.
- **Any rendered line moves the config hash.** `ComputeConfigHash`
  ([`configmap.go:293-305`](../../internal/builder/configmap.go)) hashes both data configs and the
  Sentinel config into one value, stamped on the data template
  ([`statefulset.go:153`](../../internal/builder/statefulset.go)) and the Sentinel template
  ([`sentinel.go:234`](../../internal/builder/sentinel.go)) and compared by `podNeedsUpdate` and
  `sentinelPodNeedsUpdate` in [`rolling_update.go`](../../internal/controller/rolling_update.go).
  A new line therefore rolls every data and Sentinel tier, and on a `spec.replicas: 1` cluster
  without Sentinel it can delete a non-persistent single pod with its dataset (via
  `singlePodDeferral`,
  [`pod_security_migration.go:128-150`](../../internal/controller/pod_security_migration.go)). The
  only existing exclusion from the hash is `GenerateValkeyConfForHash`
  ([`configmap.go:50-58`](../../internal/builder/configmap.go)), which leaves out the known-master
  runtime state.
- **The check that would guard the pins is a required gate.** The job `Valkey Image Tools`
  ([`release.yml:624-657`](../../.github/workflows/release.yml)) runs `make test-image-tools` on
  every pull request to `main` and is a required status check. Renovate caps the pins per major
  ([`renovate.json:212`](../../renovate.json), [`:223`](../../renovate.json)), so a new major
  arrives as a human PR that runs the same check.
- The candidate host test, `TestRestrictedRuntime_ValkeyServerPersistsAndAnswers`
  ([`restricted_runtime_test.go:99`](../../test/imagetools/restricted_runtime_test.go)), loops over
  both pinned images and starts `valkey-server` with flags and no config file
  ([`:107`](../../test/imagetools/restricted_runtime_test.go)), so a `CONFIG GET` there reads
  exactly the compiled default the generated config relies on. It is ADR 0017 D53's
  restricted-posture test, and D53 does not mention configuration defaults.

**Impact.** None on any known image. Should an image with a `yes` default ever run: the principal
is any client reaching the data port (no password without `spec.auth`, since auth is opt-in under
[ADR 0016](../adr/0016-authentication-and-tls-posture.md) D1 and `protected-mode no` is always
rendered; otherwise the one cluster password). It already holds the default user with `+@all`.
`DEBUG` adds little; `MODULE LOAD` is the substantive residual and needs a loadable object on disk,
which the read-only root filesystem and fixed `dir`/`dbfilename` prevent while
`enable-protected-configs` stays `no`. Nothing in the repository states or checks the default today.

## Required changes

Depends on the answer to Q1:

- **Under B:** in `restricted_runtime_test.go` (or a sibling function in `test/imagetools`), read
  each switch with its own call, for example
  `echo "enable-debug-command:$(valkey-cli config get enable-debug-command | tail -1)"`, and
  `assert.Contains` `enable-debug-command:no`; the same for the other two. Optionally assert that
  `DEBUG SLEEP 0` answers `DEBUG command not allowed` and `CONFIG SET dir` answers
  `can't set protected config`. `make test-image-tools` is green; mutation: expecting `yes` turns
  it red.
- **Under B:** amend ADR 0017 D53 and [`docs/developer/testing.md`](../developer/testing.md) (the
  table row and the "Image tools" section) to say the tier checks these defaults.
- **Under A2:** add the three lines as `no` to the `# General` block of the ConfigMap content and
  keep them out of the hash input next to `GenerateValkeyConfForHash`. Unit tests: the ConfigMap
  carries the three lines; `ComputeConfigHash` does not move with them; the exclusion is pinned to
  exactly these three constant lines. Add them to the directive table in
  [`secrets-and-tls.md`](../security/secrets-and-tls.md).

Under either option:

- Record the decision in ADR 0016 (it holds the Valkey server-side posture); under B, name A2 as the
  next step should the check turn red.
- Rewrite H-7 to its final form: the heading describes what was taken, drop the "Not verified: the
  images themselves" line (measured) and the sentence that nothing states or checks the value.

## Open questions

### Q1: Should the generated config state the three switches, or should the operator rely on the image default and check it on the pins?

Every upstream image already defaults to `no`, so neither option changes behaviour on any known
cluster. The difference is whether the value is stated in the config (without paying a fleet roll)
or a changed default is caught as a red required check on the pin-bump PR.

- **B - render nothing, assert the compiled default on both pins (recommended).** No roll, no
  ConfigMap change. Cost XS. Leaves open a custom build with a changed default, or a new major run
  in production before the pins cross; neither exists anywhere known.
- **A2 - render the three lines as `no`, excluded from the config hash.** No pod rolls. Cost S.
  Adds a second hash exclusion that a later edit could reuse to make a real config change skip its
  roll; the lines take effect only at an unbounded next pod recreation, so in the one case where
  they matter the ConfigMap says `no` while the running server still allows the commands; and a
  build that flips a compiled default can ignore the line as well.

B is recommended: it closes the only realistic path for a changed default, an upstream release,
at the pin-bump PR behind a required check, and changes nothing on any cluster. A2 stays the ready
next step if that check ever turns red.

**Answer:** _open_
