# T43 - static checks and ci gates do not reach build-tagged tests, the standing constraints or the chart

**Scope.** Three rules of this repository are held by review or by hand instead of by a required
check; all hold on the current tree, and each gap lets the next regression merge green. The parts
share the gates they land in (`Code Linting`, `Unit Tests`), the "test as lint" precedent
[`rbac_drift_test.go`](../../internal/controller/rbac_drift_test.go), and one build-tag list.

- **Lint and vet of build-tagged tests**: no static-analysis target passes a build tag, and two
  tagged e2e files are compiled by no CI job.
- **Static-analysis net for the standing constraints**: no fleet-wide reconciler state, no metric
  written from a reconcile pass, an ownership guard before every write and delete.
- **Chart render gate**: no CI job renders the Helm chart's non-default paths or checks its
  refusals.

## Current state

**Shared facts.** `Code Linting` ([`release.yml:498-519`](../../.github/workflows/release.yml))
runs only `make lint` on every PR to `main`, installs no `helm`, and is required. The required
contexts are the twelve of [ADR 0017](../adr/0017-test-and-ci-policy.md) D47, held in repository
ruleset "main" (id 23985346), not in classic branch protection. `rbac_drift_test.go` locates the
tree with `repoRoot` ([`:63`](../../internal/controller/rbac_drift_test.go#L63)) and parses YAML
with `k8s.io/apimachinery/pkg/util/yaml` (`:30`), so a test of that shape needs no new module.
`make cyclo` ignores `_test.go`; complexity under 15 in new test code is a review item.

## Open questions

### Q1: Where does the build-tag list live? (lint and vet)

It decides which required job fails on a compile error, vet or lint finding, unused helper or bad
formatting in tagged test code; it does not change which tests run or the `vet`, `build`, `test`
and `run` targets.

- **A - `run.build-tags` in `.golangci.yml` only, `Makefile:84` deleted (recommended).** One line
  in the already-required job: typecheck, `govet`, `unused`, `staticcheck` and the formatter all
  see the tagged files, and the list reaches `make lint-fix` and editors. Cost S if the first run
  is small.
- **B2 - the tags on the `go vet` line of `lint` only.** Full vet on the tagged files, nothing
  else. Cost XS to S.

A closes both halves at the same cost and catches exactly the dead e2e helpers; B2 lands first
only if the first measured run is larger than S, and A follows after the cleanup.

**Answer:** _open_

### Q2: How does the tag list stay complete when a tier is added? (lint and vet)

After Q1 A the list is enumerated by hand, and a missed tag reopens the gap silently. Both options
include the ADR 0017 D56 rule and the checklist entry.

- **A - the rule and the checklist entry only.** Docs only; a missed tag waits for review, and it
  departs from ADR 0017 D42 ("a hand-maintained one is theatre") and must say why.
- **B - plus a two-sided unit drift test (recommended).** An untagged test in
  `internal/controller` (next to `rbac_drift_test.go`, or in the standing-constraints file) parses
  each `//go:build` line with `go/build/constraint`, collects the un-negated tags (`e2e && e2e_helm`
  yields both, `!ignore_autogenerated` none) and asserts set equality with `run.build-tags`. About
  50 lines plus revert checks.

B, because both sides of the list live in this repository, the shape ADR 0017 D42 guards from both
sides; it also goes red if `chart` (Q5 A2) is not listed, or `e2e_helm` outlives
`migrate_e2e_test.go` (T44).

### Q5: How is the chart check written? (chart gate)

Posture can be checked by restating fields or by running the Pod Security evaluator on the
rendered pods.

- **A - shell script under `hack/` plus a Makefile target.** Cost S, no module. Every posture row
  restates fields, the shape ADR 0017 D52 rejects for the admission question; grep cannot reliably
  tell pod-level from container-level `securityContext`; no linter covers the script.
- **A2 - build-tagged Go test that execs `helm`, with the Pod Security evaluator (recommended).**
  For example `test/chart/` under `//go:build chart`, `make test-chart`: decode into
  `appsv1.Deployment` and `batchv1.Job`, evaluate both pod templates with
  `k8s.io/pod-security-admission` at `restricted`/`latest` on every row, plus a positive control
  that strips `securityContext` and must be denied; field checks only for what `restricted` does
  not require; ten named negative subtests; fails, never skips, without `helm`. Cost S, no new
  module; linted once `chart` is in `run.build-tags` (Q1 A); the evaluator is the library's
  profile, not the cluster's.

A2 alone admits the hook Job's pod in PR CI with the checks the API server runs, at A's cost and
without restating fields.

### Q6: Where does the chart check run in CI? (chart gate)

A job gates a merge only if it is a required context in ruleset 23985346; the hosting job needs
its own `setup-helm` step either way.

- **(i) New job, e.g. `Helm Chart`.** Clearest failure name, parallel, follows the image-tools
  precedent. Needs an admin edit of the ruleset, an entry in `semantic-release`'s `needs:`

- **(ii) Step in `Code Linting` after `make lint` (recommended).** With
  `if: success() || failure()` so a lint failure does not hide it. Cost XS, no ruleset, `needs:`

(ii) gates as strongly as (i), because `Code Linting` is already required, without three edits
including an admin action.
